Error taxonomy

Two kinds of failure exist and they are easy to confuse. Transport errors mean the API could not answer. Reason codes mean the chain contained something the protocol declined to act on.

Never surface a reason code as an outage

A failed mint is a successful API call. If your client shows "service error" when the real answer is "your reveal was 12 blocks early", you have hidden the one fact the user needs.

Status codes

What each status means and how a client should behave.
StatusMeaningRetry
200Answered. This includes empty lists and artifacts that do not exist yet from your point of view.Not applicable
400The request is malformed: an unparseable cursor, a bad id, a body that is not JSONNo. Fix the request.
404No such artifact, carrier, or epoch at this indexed heightOnly if the indexer was behind. Check indexed_height first.
413The request body is too large, for example too many outpoints in one safety checkNo. Split the batch.

Error body

{
  "error": {
    "code": "NOT_READY",
    "message": "indexer is replaying after a reorg",
    "indexed_height": 0,
    "tip_height": 0
  }
}
  • code is a stable string your software can branch on.
  • message is for humans and may change. Do not parse it.
  • Sync heights are included where they are known, because most transient failures are really a sync story.
Not frozen by the baseline

The baseline fixes the endpoints and their success payloads. It does not fix the error body. The shape above is what this stack uses and what clients should expect from it, but treat the status code as the contract and the body as a convenience.

Fail closed

The rule the whole stack follows: when the truth is unavailable, say so. Never substitute.

  • An unreachable indexer produces an error, not a cached number presented as current.
  • An indexer that is behind answers for the height it has reached, and says what that height is.
  • A proxy that cannot reach the indexer returns an error rather than an empty list, because an empty list is a claim that there is nothing.
  • A client that cannot fetch shows an empty state that says the data could not be read. It does not show a zero.
Zero and unknown are different

"artifacts_alive": 0 is a measurement. A missing response is not. Any interface that renders them the same way is lying by omission, and that includes progress bars, charts, and share cards.

Client checklist

  1. Read /status first and keep indexed_height alongside anything you cache.
  2. Treat 503 as normal during sync and reorg replay. Back off, do not alarm the user.
  3. Back off exponentially on 429, 500, and 503. Do not retry 400, 404, or 413.
  4. Set a request timeout. A hung request should surface as an honest empty state.
  5. Show the height every number was read at.
  6. Never invent a value to fill a gap in a layout.

Reporting a suspected bug

If the API answers but the answer looks wrong, that is not an error taxonomy problem, it is possibly a state disagreement. Collect /status from both implementations, find the first height where they differ, and follow Report a disagreement.
